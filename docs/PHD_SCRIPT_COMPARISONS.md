## `e()` vs `e` and nullary operations

Investigation used `input/b2.ua` (nullary op `e`) on the repo JAR.

| Input | Java `Terms.stringToTerm` | Meaning | `intEval` with `{x:0}` only |
|-------|---------------------------|---------|-----------------------------|
| `e` | Parses as `VariableImp` | Variable named `e`, not constant | Java: NPE (no binding for `e`) |
| `e()` | **IAE `empty string`** | Not supported | (parse fails) |
| `f()` | **IAE `empty string`** | Same for any nullary `op()` | (parse fails) |
| `x` | Variable | — | OK |

Java rejects **all** nullary syntax `op()` in `Terms.stringToTerm` (empty argument list after the `(…)` split). This is a **Java parser limitation**, not a special case for `e` alone.

Jamie’s workaround in `dmm.py`:

- **pyparsing** grammar requires `e()` (and `f()`, …) for constants.
- **`to_term()`** rewrites bare `e` in argument positions to `e()` via regex before parsing.
- **`_to_term`** builds `NonVariableTerm.makeConstantTerm(OperationSymbol(op,0))` instead of calling `Terms.stringToTerm` for constants.

`NonVariableTerm.makeConstantTerm(OperationSymbol("e",0))` **does** evaluate on `b2` (`intEval` → `1`).

**org.uacalc / uacalc_lib (Rust)** mirror Java for bare `e` (variable). For `e()` they **differ from Java**: `string_to_term("e()")` succeeds and evaluates like the constant (see `test_nullary_string_to_term_java_parity.py`, strict xfail on `Terms.stringToTerm("e()")` expecting Java IAE). This is documented; this PR does not change the shim to reject `e()`.

Probe golden: `tests/jython_scripts/phd/probes/nullary_string_to_term.py` → `goldens/nullary_string_to_term.py.stdout`.

## pyparsing vendoring

MIT **pyparsing 2.4.7** is vendored at `tests/jython_scripts/_vendor/pyparsing.py` (unmodified licence header). Both Jython golden regeneration and the CPython harness prepend `_vendor` on `sys.path` so scripts that `import pyparsing` run without editing script logic.

**Print statements:** Jython‑2 `print` statements in copied scripts are converted to `print(...)` at **load time** in `tests/jython_scripts/harness.py` (`convert_print_statements_to_function`). On-disk copies stay Jamie’s originals aside from the harness header comment.

2. **mace4 / pyparsing algebras** — Anonymous operation tables from Mace4 models; shim `IntOperation` range check fails on `KR-1gen.model`.

4. **check_crl** — Needs a true CRL algebra input, not `b2`.
5. **twist.py** — Py3 `print(..., end=)`; Jython 2.7 cannot parse; no UACalc API.
